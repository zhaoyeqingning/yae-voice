# 提交规范

导师按 GitHub 上的提交记录给组员打分。每条记录都要能单独回答三件事：谁做的、做了哪一个行为、怎样确认这个行为是好的。

检查由仓库里的「提交检查」自动执行。标题或验证命令不合格，推送会被拒绝。一次推送里的每一条提交都会被单独检出并运行测试，中间有一条测试失败，整次推送失败。

## 一次提交只做一件事

一次提交只包含一个能观察的行为，或者一次不改变行为的整理。提交完成后，把工作区停在这次提交上，`pytest` 必须通过。

因此这些情况不能进入历史：

- 同一次提交里既改播放、又改转写、又改页面
- 测试还是失败的半成品
- 代码进了提交，对应测试留在下一次
- 标题写「更新」「修复」「WIP」

`feat`、`fix`、`test` 必须带上这次行为的测试文件。`refactor`、`docs`、`chore` 不改变既有行为，可以不新增测试，但已有测试仍须通过。

## 标题

```text
类型(范围): 这次做了什么
```

范围可以省略。类型只用下面六种。

| 类型 | 用于 |
|------|------|
| feat | 新增一个能被测试观察到的行为 |
| fix | 修正一个已经存在的行为 |
| test | 只补充测试，不改行为 |
| refactor | 整理结构，行为不变 |
| docs | 只改文档 |
| chore | 依赖、忽略规则、检查脚本这类工程杂事 |

标题整行不超过 72 个字符。冒号用英文冒号，冒号后有一个空格。说明至少 4 个字，并且写出行为，例如「新一轮会取消上一轮播放」。

## 正文

标题下面空一行，然后写验证命令。

```text
feat(session): 新一轮会取消上一轮播放

验证：pytest tests/test_session.py::test_new_turn_cancels_previous -q
```

`feat`、`fix`、`test` 的验证命令要点名测试文件或具体测试，例如 `tests/test_session.py` 或 `tests/test_session.py::test_new_turn_cancels_previous`。点名的测试文件必须出现在这次提交里。

`refactor`、`docs`、`chore` 写全量测试即可：

```text
docs(commit): 补充提交记录的阅读方式

验证：pytest -q
```

验证命令使用 `pytest`，路径用 `/`。提交前先运行这条命令，再运行 `pytest -q`。两条都通过后再提交。

## 合并

组员在自己的分支上提交，用合并请求进入主分支。仓库关闭了压缩合并和变基合并，只保留「创建合并提交」。这样主分支上仍能看到每个人的原始提交。

不要用 `git commit --amend` 改已经推送的提交，也不要强推主分支。已经推送的记录就是评分依据。

组长在搭建骨架时可以直接提交到主分支，每次仍须满足本规范。

## 身份

提交的名字与邮箱使用组内约定账号即可。同一仓库可由多名组员轮流署名；邮箱须能对应到 GitHub 上的组员账号。

## 反例

```text
更新
```

```text
feat: 修复

验证：pytest -q
```

```text
feat(player): 播放器会丢掉过期音频

验证：pytest -q
```

第三条的问题：`feat` 却没有点名这次的测试。应写成 `pytest tests/test_player.py::test_drop_stale_audio -q`，并且这个测试文件就在本次提交中。
